# Trader Stock Generator Deep Audit

**Baseline:** STALKER 2 runtime/game + DLC CFG dump 2.0.5  
**Patch-coordinate source:** `generator-local-source-*` raw/local layer  
**Purpose:** map trader inventory generation completely before any trader-stock UI control is designed.

## 1. Verdict

Trader stock is substantially cleaner than generic NPC loot, but it is **not one global pool**. Real stock is assembled from concrete trader generators, reusable T1–T4 stock pools, medic/bartender pools, and a handful of cross-context dependencies. A safe future control must therefore use an explicit trader-only allowlist and must never treat every generator with a trader-looking name as interchangeable.

No runtime writer behavior is changed by this audit.

## 3. Stock progression and refresh are separate mechanisms

`PlayerRank` is the dominant stock gate inside `ItemGeneratorPrototypes.cfg`. Difficulty is almost absent from the active trader surface. Trade refresh is defined separately by `TradePrototypes.cfg`; price discounts are also separate from stock generation.

| Mechanism | Observed trader-domain mapping | Interpretation |
| --- | --- | --- |
| `PlayerRank` on generator category blocks | 176 / 220 blocks | primary stock-progression axis |
| `Diff` on generator category blocks | 6 / 220 blocks | all six belong to unresolved `HimzavodTrader_ItemGenerator`; not a general trader-stock axis |
| `ReputationThreshold` on generator category blocks | 4 blocks | all four are in `DynamicTraderItemGenerator` (`-500`); do not generalize to all traders |
| Per-category `RefreshTime` | 5 blocks | only `DynamicTraderItemGenerator`, all `1h` |
| Mapped `TradePrototype` refresh | 80 × 8h; 1 × 1d; 2 × 7d | stock refresh belongs to the TradePrototype layer |
| TradeGenerator `ConditionSID` | 83 / 83 mapped links are `ConstTrue` | rank-based Buy/Sell discounts are not stock-gating conditions |

## 7. Internal category names are not reliable gameplay labels

Within the trader surface itself, enum categories are overloaded. `Artifact` includes true anomaly artifacts **and** grenades/binoculars; `Junk` contains weapons and armor. Therefore a future trader control must select exact SIDs or a proven item taxonomy, never simply `Category == Artifact` or `Category == Junk`.

## 10. Exact-source anomalies / special cases

- `BartenderCNPP_TradeItemGenerator` has a raw `Consumable` row that contains both `ItemPrototypeSID = Sausage` **and** `ItemGeneratorPrototypeSID = empty`, plus `Chance=1` and `Weight=4.f`. This is preserved literally; do not normalize it into a normal item-only row.
- `DynamicTraderItemGenerator` is the only mapped trader-domain generator with local `ReputationThreshold=-500` and per-category `RefreshTime=1h`; its weapons also use non-full durability and large attached-ammo counts. It is not a template for ordinary traders.
- `HimzavodTrader_ItemGenerator` contains all six observed trader-domain `Diff`-gated category blocks but has no resolved runtime consumer in the supplied CFG graph. It is excluded until proven active.

## 11. Future writer rule

A trader-stock control is not supported merely because a matching item exists in a trader generator. The target set must be generated from **raw/local rows**, must have a trader-only blast radius or an intentional cross-context scope, and must keep `PlayerRank`, stage-specific wrappers, refresh, and item-category quirks intact.

For exact per-row data, see [`TRADER-ENTRY-CATALOG.md`](TRADER-ENTRY-CATALOG.md).
